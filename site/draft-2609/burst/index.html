New · Nagi Burst · 27 Sep 2026

Every control.
One forward pass.

Burst sets all K controls of a real-time machine from a single forward pass of a 27B Nagi model, instead of one pass per control (K-call). The same weights serve both readouts and return the same output: a probability for every option of every control. It helps when a machine has several controls and the world does not wait for the model.

Ships as Nagi-ENORMOUS Burst: the released Nagi-ENORMOUS adapter (rank-8 LoRA on Qwen3.8-27B) trained for 417 more updates on both formats. Burst needs these weights; the earlier adapter never saw the Burst format.

Preregistered real-time confirmation on 24 fresh seeds × 3 games: Burst survived longer than Jev in 67.4% of head-to-heads (95% CI [57.7%, 77.0%]), a preregistered superiority result. Per game, the lead is significant on Booster Gauntlet only. Decision latency: 248 ms p50 with three controls at 3 streams per H100 in the preregistered latency check, 264 ms in play.

What we claim

  • Burst decides all K controls with one forward pass, on the same weights as one pass per control.
  • Decision latency p50 of 248 ms (3 controls) and 196 ms (4 controls) at 3 concurrent streams on an H100 (merged bf16, fused kernels). The one-sided 97.5% upper bounds, 269 and 264 ms, are under the preregistered 300 ms limit. In play on the release run the p50 was 264 and 290 ms.
  • Multi-control decision quality is non-inferior to one pass per control of the same weights within 0.06 (MA1 difference −0.005, one-sided 97.5% bound −0.045).
  • Through the SDK, answers do not depend on the order in which the client lists the controls, given the environment's declared order. The model itself changes its answer on 24.8% [17.5%, 32.2%] of states when the order is rotated.
  • Burst outperforms Jev in real-time head-to-heads: on 24 fresh seed indices × 3 games it survived longer in 67.4% of them (95% CI [57.7%, 77.0%]; sign-flip p = 0.0018).
  • Per game, only on Booster Gauntlet (97.9% of head-to-heads, significant after Holm correction).

What we do not claim

  • That Burst beats Jev on Snake Rush or Rotorwash-Ramp. Neither is individually significant, and on Snake Rush Burst survived longer in under half of the head-to-heads.
  • An order-invariant model. The SDK fixes the order of the controls; the model itself still changes its answer when the order changes.
  • Better decisions than one pass per control. With time frozen (lockstep), Burst was worse on the helicopter game. Its advantage is latency.
  • Anything from the 10-seed screen beyond a screen, including Burst's lead over one pass per control in real time.
  • Results for other games, K ≥ 5 controls, other GPUs or serving paths, or anything about Jev's size or hardware.
  • A new mechanism. Reading several discrete actions from one pass is known (e.g. OpenVLA-OFT, action branching).

01 / The problem

Latency is error in control.

A helicopter in a collapsing cave has three controls: collective, cyclic and winch. The game advances every 250 ms whether or not the model has answered. An answer that arrives late acts on a state that no longer exists; an answer that has not arrived means the previous controls keep running.

Nagi answers a question by reading option-letter probabilities from one forward pass. With K controls, the plain way is K-call: one forward pass per control, one after the other. At three controls that is three passes per tick, and on an H100 they do not fit in 250 ms.

This is not a small effect. In our previous test the same K-call model reached a normalized score of R = 0.324 on the helicopter game when time was frozen (24 seeds) and 0.108 when it had to keep up with the clock (5 seeds). It survived 75.1 s on average frozen (24 seeds) and 22.9 s in real time (5 seeds). So we rank models only in real time: the world never pauses, and latency is never subtracted or normalized away. A benchmark that freezes time measures a product nobody can run.

The frozen real-time rules (same for every player)
  • Clock: 4 Hz (250 ms ticks). At each tick, collect a finished reply, then send a new request on the current state if none is in flight. One request in flight per stream.
  • A reply is applied at the first tick after it arrives. A reply older than 1,000 ms is stale: rejected and logged.
  • Persistent controls hold their last value; after 1,000 ms without an applied reply they reset to the game's safe default (an expiry reset).
  • If the harness itself processes a tick more than 100 ms late, the round is void: replayed once with the same seed, then dropped from both sides of every comparison. More than 1 void in a 10-round screen invalidates the whole cell.
  • Latency is measured end to end on the serving path: prompt rendering, tokenization, forward pass(es), readout and, for an API, the network round trip.

02 / How Burst works

K answer slots, one pass.

The readout

Burst renders one prompt: the state, then every control with its lettered options, then an answer block with one slot per control. Each slot is a marker [k] followed by a blank token □:

STATE:
<state>

CONTROLS (choose all at the same time):
[1] collective: A) <option>  B) <option>  C) <option>
[2] cyclic: A) …  B) …  C) …  D) …
[3] winch: A) …  B) …  C) …

ANSWER:
[1]□
[2]□
[3]□

One forward pass over this prompt. For slot k we take the hidden state hk at the last token of [k] and project it only onto the letter tokens of that control's options, through the model's own output head:

pk = softmax( softcap(hk · Wletters(k)) / T ), answer = argmax. T = 1.0.

The token after each [k] is always the blank, never an answer, so no slot sees another slot's choice. The K distributions are read in parallel and are conditionally independent given the prompt. Training targets for each slot are the max-marginals of an exact joint oracle, so that per-slot argmax recovers the best joint action when it is unique. Ties are the known failure mode of this design, and they matter below.

03 / Evidence

Survive longer when the clock is real.

Arena v3 is a set of three fail-first games: difficulty rises every tick, on the same schedule for every player, until everyone fails (cap 60 s, six 10 s levels). The metric is simple: on the same seed, whoever fails later wins that head-to-head; a tie counts ½. We average over opponents, then over games. It is invariant to how the difficulty ramp is shaped.

Snake Rush
1 control (direction). Speed and walls ramp up. Burst has nothing to save here.
Rotorwash-Ramp
3 controls (collective, cyclic, winch). Helicopter in a collapsing cave.
Booster Gauntlet
4 controls. Consecutive rocket landings with rising wind and heavier engines. The least-seen game for Nagi.

    Same weights: the gain is speed, not judgment

    Because Burst and K-call share weights, comparing them isolates the readout. Burst's first test gives a consistent picture: with time frozen, the two make decisions of the same quality, and K-call even gets three passes per move to Burst's one. Once the clock is real, the direction reverses, because Burst's answers arrive in time. That reversal rests on a 5-seed exploratory run and the 10-seed screen; there is no preregistered real-time test of Burst against K-call.

    Versus Jev, the faster player

    Jev (version 1.13.0, a commercial API) answers all controls in one request, like Burst, and was the fastest player on the two multi-control games: p50 212 and 214 ms including the network, fresh on 88–90% of ticks against Burst's 66%. In the Board 1 screen Burst still survived longer in 70% (Snake Rush), 90% (Rotorwash-Ramp) and 100% (Booster Gauntlet) of head-to-heads. Against a faster opponent, a lead cannot come from speed; it has to come from the decisions, including Nagi's training on similar tasks (below). The screen picked Burst after the fact, so the preregistered test on 24 fresh seeds is the result that counts: 67.4% ([57.7%, 77.0%]). It passed the superiority test, but the lead is uneven: 97.9% on Booster Gauntlet, 58.3% on Rotorwash-Ramp and 45.8% on Snake Rush, and only Booster is individually significant.

    Caveats: Jev runs on unknown vendor hardware over the network from a recorded client region; its latency includes the network and is not subtracted. In the release run the first Jev job stopped at its per-job cost guard before Rotorwash-Ramp indices 25–33; a second job played them, and Jev's measured p50 there was 297 ms against 172 ms in the first job (3 streams, latency probe). Jev's answers are not deterministic on repeated identical requests; its version string (jev-1.13.0) matched Board 1 in every job. Nagi was trained on similar control tasks (hover, crane, closed-loop snake); Jev's training is unknown. This is a specialist against a general model, on the specialist's kind of task.

    What this benchmark measures, and what it does not

    Measures

    • How long a model keeps a machine alive under rising difficulty, with real latency, on a pinned serving path.
    • Paired comparisons on identical seeds and identical difficulty schedules.
    • Latency, freshness, stale replies and expiry resets per player, per game.

    Does not measure

    • General intelligence, language ability or anything outside these three games.
    • Hardware-matched speed: Jev's hardware is unknown; self-hosted players share one H100 class.
    • Reading brand-new rules: Nagi trained on similar tasks, which we flag rather than hide.

    04 / Limitations and what failed

    The parts that did not work.

    • Failed a preregistered gateBurst was prototyped as “Chord”. That first prototype failed its preregistered order gate: rotating the order in which the controls are listed changed the joint answer on 26.0% of 500 states [18.4%, 34.3%], against a 10% limit. The verdict was REJECT, and it stays REJECT; it is never passed retroactively. Board 1's Burst player used that same readout.
    • The fix, tested as a new candidateTwo variants, with gates frozen before any data. A: the SDK always renders the controls in the environment's declared order, so the served answer cannot depend on the order a client lists them in. This is a software guarantee, not a property of the model: presented in another order, the model still changes its answer on 24.8% of states, and clients that bypass the SDK must use the canonical order. B: render the state under the K rotations of the control order, score the K prompts in one batched forward pass, and average each control's log-probabilities, so every control sits in every slot once. B costs K× the tokens of A and was predicted to miss the latency limit. It did (p50 774 / 1,039 ms on Rotorwash-Ramp / Booster), and its order residual missed too (9.0%, upper bound 13.2% against 10%). Selected by the frozen rule: A (canonical order). Every gate of variant A passed.
    • Ceiling crashes in real timeOn the 24 fresh-seed Rotorwash-Ramp rounds, 12 ended on the cave ceiling (collapse 9, terrain 3). The preregistration requires disclosing this at 50% or more. The offline climb-bias gate (G3) passed, but it detects only gross bias.
    • No coordination gainWe hoped reading all controls together would improve coordination between them. It did not: the preregistered “clear win” test on coordination states failed (MA2 −0.016 [−0.113, +0.072], MA2b +0.010 [−0.078, +0.088]).
    • Worse flying with time frozenIn frozen-time Rotorwash, Burst hit the cave ceiling in 24 of 24 rounds and survived 43.1 s less than K-call [−53.0, −32.0]. The real-time advantage exists in spite of this.
    • Screen-level evidenceBoard 1 is a screen: 10 seeds per game. Burst was picked as the best of four Nagi entries after the results, which inflates its numbers (winner's curse), and two of the four share weights. That is why the release test runs on fresh seeds under a preregistration. It compares Burst with Jev only; Burst versus one pass per control in real time has only this screen and a 5-seed exploratory run. The preregistration bounds the selection optimism at about 0.076 in win-rate units at n = 10.
    • A player we could not rankCLM-8B was entered but failed its own conformance gate (rule D15), so it is not ranked. Board 1 therefore has 6 players, and Burst was selected against 2 external models (Jev, SemIf-4B), not 3.
    • In-domain trainingBurst's weights, K-call's and ENORMOUS-CL's were trained on similar machine tasks (hover, crane, closed-loop snake). This was intended and is flagged on every row. No game engine, seed or state from the Arena appears in training (audited). External players' training is unknown.
    • A timing wall in Booster GauntletEach landing must happen within 22 s, and many of the strongest rounds end at exactly 22.0 s. Those head-to-heads are ties, so Booster separates strong from weak players more than it separates the strong ones.
    • Trained on three controlsEvery Burst training row had K = 3 slots (with the control order shuffled per row). Booster Gauntlet's K = 4 is outside the trained range, and K ≥ 5 was never evaluated. Two genres were held out of training; on them every readout is weak (joint decisions acceptable: 0.17 Burst vs 0.18 K-call, 120 instances).
    • One control, no gainWith K = 1 (Snake Rush) Burst does one pass either way and is slightly slower (231 vs 213 ms p50) because its prompt is longer. On Snake Rush every model sits near the floor: Burst's median survival (10 s) is below that of the naive reference bot (13.75 s).
    • The baseline is sequentialK-call here is the SDK default: K forward passes one after another. We did not measure a K-call that batches its K prompts or caches the shared state prefix. Such a baseline would close part of the latency gap, at the cost of more tokens.
    • Uneven lead over JevThe superiority result is carried by Booster Gauntlet (97.9% of head-to-heads). On Rotorwash-Ramp (58.3%) and Snake Rush (45.8%) the difference from Jev is not significant, and Booster’s 22 s wall means Burst “wins” there by reaching the wall while Jev fails earlier. Jev’s measured latency also differed between its two release jobs (p50 172 vs 297 ms); without the second job’s 9 rounds the win rate is 65.7% [54.3%, 77.1%], still above 50% (a sensitivity check, not preregistered).
    • Hardware and servingAll self-hosted numbers: H100 80 GB, bf16 weights with the adapter merged, fused kernels, 3 streams per GPU. Other GPUs, quantization or batch sizes will give other numbers. Nothing here is a service-level guarantee.
    • Training historyA preregistered pause fired at step 125 of 417 (language benchmark −2.07 points) and was overridden by the project owner; the run continued. At the final step the language score is −0.5 points vs the released ENORMOUS (0.8578 vs 0.8631, n = 200); Arena retention against it was inconclusive, and the public benchmark suite was not re-run.
    • ProbabilitiesTemperature 1.0 is not learned calibration; probabilities can be overconfident on new domains. Held-out genres in the offline test rest on 2 families only.
    • Who ran thisNagi's developers designed, ran and analysed every test on this page. Everything needed to check it is linked below.

    05 / Reproduce

    Check it yourself.

    python -m pip install "nagi-decisions @ git+https://github.com/nagisanzenin/nagi.git@v0.6.0"

from nagi import load_enormous_burst   # 80 GB GPU, BF16, adapter merged in place
nagi = load_enormous_burst()
state = "tick 3: water 0.4 m\n\nCONTROLS (set together each tick): gate = closed | open; pump = down | idle | up."
questions = {"pump": {"type": "choice", "instructions": "Choose the pump setting.", "criteria": {"down": "pump water out", "idle": "leave pump idle", "up": "pump water in"}},
             "gate": {"type": "choice", "instructions": "Choose the gate setting.", "criteria": {"closed": "gate stays closed", "open": "gate is open"}}}
out = nagi.system_one(state, questions, mode="burst")   # one forward pass for every control
print({qid: a["choice"] for qid, a in out["answers"].items()}, out["burst"])

    Needs an 80 GB GPU in bf16 (the base alone is about 56 GB). The answer dictionary has the same shape as the default K-call mode; out["burst"] reports the slot order used (here taken from the CONTROLS line, not the dict order) and the number of forward passes.

    Prior art

    Parallel decoding of action dimensions in one pass: OpenVLA-OFT (Kim, Finn, Liang 2025, arXiv:2502.19645). Shared trunk with independent per-dimension heads: action branching (Tavakoli et al. 2018, arXiv:1711.08946), OpenAI Five (2019). Letter-symbol multiple-choice readout: Robinson et al. (ICLR 2023, arXiv:2210.12353). Independent parallel predictions and the multimodality problem: Gu et al. (ICLR 2018, arXiv:1711.02281). Burst combines a letter readout through the existing LM head at K slots with max-marginal slot targets; we did not find this exact combination, but each piece is standard.
